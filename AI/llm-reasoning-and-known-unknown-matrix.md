# LLM의 '잘못된 확신(Unknown Unknown)'은 내부 반성으로 소거할 수 없으며 오직 기계적 실측으로만 교정된다

## 🤔 헷갈렸던 점
- 모델의 추론 능력이 향상되면 프롬프트에 "틀린 점을 스스로 비판하라"고 지시하는 것만으로 모든 환각과 오류를 걸러낼 수 있을 것이라 생각했다.
- "모른다"고 인정하는 것(Known unknown)과 "완벽히 확신하며 틀리는 것(Unknown unknown)"이 모델 내부에서 어떻게 갈리는지, 왜 최신 모델도 결정적 순간에 그럴듯하게 거짓말을 하는지 와닿지 않았다.

## ✅ 정리
- **LLM 관점에서의 인식의 4범주 (Known/Unknown Matrix)**:

| 구분 | 안다는 것을 인지함 (자각) | 인지하지 못함 (무자각) |
| :--- | :--- | :--- |
| **실제로 앎 (True)** | **Known known** (검증된 지식)<br>• 확신과 사실이 일치. 절차 없이 즉시 수행 | **Unknown known** (잠재 지식)<br>• 가중치 속에 있으나 표면화되지 않음. 채굴 필요 |
| **실제로 모름 (False)** | **Known unknown** (자각된 무지)<br>• 불확실성 감지. 가설-검증 루프로 해소 | **Unknown unknown** (잘못된 확신)<br>• 모른다는 것조차 모름. 가장 그럴듯하게 실패 |

- **세대 간 발전의 실체 (Known unknown 대응의 변화)**:
  1. **보정(Calibration)의 개선**: 자기 지식의 경계를 감지하여, 과거 Unknown unknown이었던 영역을 Known unknown으로 이동시킴 ("모르겠다"고 인정하는 빈도 증가).
  2. **행동의 전환**: 파라미터 속 지식을 정답이 아닌 **사전확률(Prior)**로 취급하고, 외부 환경(실행 결과, 파일, 문서)을 **Ground Truth**로 삼아 실측으로 해소.
- **핵심 한계: Unknown unknown은 내부에서 소거가 불가능하다**:
  - '확신감'이라는 감지 기제 자체가 모델 내부의 출력이므로, 잘못된 확신 상태에서는 스스로 의심이 들지 않는다.
  - 따라서 이에 대한 대응은 모델의 자아성찰(Introspection)이 아니라 **감지에 의존하지 않는 기계적 탐침(Mechanical Probing)과 외부 강제 실측**뿐이다.
- **Unknown known (잠재 지식)과 '적대적 자기 비판'의 메커니즘**:
  - 모델은 자기가 한 번에 말하는 것보다 가중치 속에 훨씬 많은 지식을 갖고 있다 (**생성-검증 격차** / **ELK, Eliciting Latent Knowledge**).
  - 사고 과정(Thinking)과 적대적 자기 비판은 가중치 깊은 곳에 묻혀 있던 지식을 수면 위로 끌어올리는 **Unknown known $\rightarrow$ Known known 변환 장치**다.
  > **자기 비판으로 잡히는 오류와 실측으로만 잡히는 오류의 경계선 = Unknown known과 Unknown unknown의 경계선.**

### 💡 핵심 정리: 4범주별 에이전트 대응 전략

```
[인식 4범주 대응 규칙]
1. Known known     ──▶ 절차/의식 없이 즉시 실행 (노력 낭비 방지)
2. Known unknown   ──▶ 감지된 불확실성을 외부 도구 실측으로 해소
3. Unknown known   ──▶ 문제 분해, 적대적 자기 비판, "틀릴 수 있는 방식 서면 나열"로 잠재 지식 채굴
4. Unknown unknown ──▶ 모델의 확신을 불신하고, 고위험 작업 시 외부 Ground Truth 강제 실측 주입
```

에이전트의 신뢰성은 모델의 주관적 확신을 믿는 데서 오는 것이 아니라, **Unknown unknown에 대비해 외부 Ground Truth를 기계적으로 실측하고 Unknown known을 체계적으로 채굴하는 아키텍처**에서 완성된다.

### 번외) 🎯 에이전트 활용 관점의 실무 함의

* **인간의 검토 우선순위**: 에이전트 출력 중 사람이 반드시 들여다봐야 할 곳은, **근거 등급이 "기억"인데 어조는 "사실"인 주장(실측 없이 확신에 차 있는 부분)**이다.
* **프롬프트 설계의 엄격한 구분**:
  * `"비판하라 / 나열하라"`류 지시는 **Unknown known 오류**를 채굴하는 데 듣는다.
  * `"실행해서 확인하라(실측)"` 지시는 **Unknown unknown 오류**를 잡는 데만 듣는다.
  * *어떤 지시가 필요한지는 오류가 어느 사분면에 있느냐에 따라 갈린다.*
* **잔여 사각지대는 외부(사용자)의 몫**: Unknown unknown은 프롬프트로 지시해도 모델 내부에서 완전히 사라지지 않으므로, **최종적인 검증 포인트는 항상 사용자 쪽에 남는다**.
