# 에이전트 추론의 핵심은 모든 주관적 확신을 가설로 강등하고 가장 강한 수단으로 실측하는 것이다

## 🤔 헷갈렸던 점
- 고품질의 에이전트 동작을 위해 모든 작업 단계마다 장황한 체크리스트와 검증 절차를 고정적으로 거쳐야 한다고 생각했다.
- 모델의 사전 기억이나 사용자가 말해준 원인 진단을 '사실(Fact)'로 믿고 추론을 시작하여 잘못된 방향으로 삽질하는 경우가 많았다.

## ✅ 정리
- **노력 배분: 절차를 위한 절차 지양**:
  - 사소하고 되돌리기 쉬운 작업 $\rightarrow$ 의식(儀式) 없이 즉시 수행 (무한 검증은 낭비).
  - 불확실하거나 실패 비용이 큰 작업 $\rightarrow$ 가설-검증 루프를 켜고 위험도에 비례해 깊이 조절.
- **핵심 루프: 확신을 가설(Hypothesis)로 강등**:
  - 무언가를 "안다"고 느끼는 순간 자문: **"이건 검증된 사실인가, 내 가설인가?"**
  - **무조건 가설로 취급해야 할 항목들**:
    - API 명세, 파일 경로, 라이브러리 버전에 대한 모델의 기억 (훈련 이후 변경 가능성).
    - 현재 세션에서 직접 파일을 열어 읽지 않은 코드의 동작.
    - "아마 되겠지", "이렇게 동작할 것이다"라는 주관적 느낌.
    - 사용자가 말한 원인 진단 (**증상은 데이터지만 원인은 가설**이다).
  - 가설이라면 즉시 최소 비용으로 검증하고, **반증 시 매몰 비용을 무시하고 즉시 계획을 수정**.
- **검증 위계: 가능한 가장 강한 수단 채택**:
  > **실행·실측 (테스트 실행/재현/직접 호출)** ──▶ **파일 직접 열람** ──▶ **공식 문서 확인** ──▶ **내부 지식 대조 (머릿속 추적)**
  - 도구로 실측할 수 있는데 머릿속 시뮬레이션으로 대체하지 않으며, 머릿속 검증만으로 "작업 완료"를 선언하지 않는다.
- **강제 의심 (Forced Doubt): 잘못된 확신의 사각지대 방어**:
  - 루프는 의심이 들 때만 발동하므로, Unknown unknown(잘못된 확신)에는 자발적으로 발동하지 않는다.
  - 따라서 **고위험 작업(보안, 결제, DB 스키마 변경, 파괴적 조작)**에서는 의심을 기계적으로 주입:
    - 실행 전 **"이 계획이 틀릴 수 있는 방식 3가지"**를 서면으로 강제 나열.
    - 확신이 강할수록 절차를 건너뛰고 싶어지며, **그 유혹 자체가 강제 의심을 실행하라는 신호**다.
- **멈춤 조건 & 정직한 보고**:
  - 증거가 수렴했거나 추가 검증 비용이 잔여 위험보다 크면 행동으로 이행 (무한 검증 방지).
  - 검증한 것과 검증하지 못한 것을 명확히 분리 보고하고, 결론마다 **근거 등급(실행/파일/문서/기억)**을 명시.

### 💡 실사용 예시: 가설-검증 추론 스킬 (SKILL.md) 적용 프롬프트

실제 에이전트 시스템(Antigravity 등)에 등록하여 사용할 수 있는 원본 스킬 명세는 별도 파일인 [📄 hypothesis-verification.md](hypothesis-verification.md)에서 확인할 수 있습니다.

```markdown
# 에이전트 시스템 프롬프트 지침 예시
1. 사용자의 증상 보고를 원인으로 단정하지 말고 가설로 수립하라.
2. 코드를 수정하기 전, 해당 파일을 직접 열람(view_file)하여 실제 구현을 확인하라.
3. 작업 완료 선언 전 반드시 테스트/빌드 명령(run_command)을 통해 실측 검증을 완료하라.
4. "검증 완료: [테스트 결과]"와 "미검증: [확인 불가 항목]"을 구분하여 최종 보고하라.
```

가설-검증 추론은 고정된 파이프라인이 아니라, **불확실성과 고위험 구간에서 주관적 확신을 데이터 기반 실측으로 교정하는 유동적 안전장치**이다.
